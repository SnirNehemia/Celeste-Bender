## About the developer
- Experienced in Python/PyTorch and ML, **new to Godot and GDScript**.
- Wants to *understand* the code, not just run it. After each change, explain what you did and why in 3–6 short bullets, and name any Godot concept involved (signals, nodes/scenes, `_physics_process`, autoloads, resources, InputMap…) in one sentence each the first time it appears.
- Plays with keyboard only.

## Tech
- **Godot 4.x, GDScript** (standard build, not .NET). Check the version with `godot --version` before relying on version-specific APIs.
- 2D, internal resolution 320×180, integer scaling, `texture_filter = nearest`.
- Physics: `CharacterBody2D` for the player and enemies; custom movement code, not RigidBody, for anything that needs to feel precise.

## Code style (important)
- **Heavily commented.** Every script starts with a header comment saying what it is and how it connects to other nodes. Comment the *why* of every non-obvious line, especially movement math.
- **Explicit names**: `max_run_speed`, `coyote_time_remaining`, not `spd`, `ct`.
- **Static typing everywhere**: `var max_run_speed: float = 90.0`, typed function args and returns.
- **Modular**: one responsibility per script. Abilities are separate component nodes (`GlideAbility`, `GustAbility`, `FlameJetAbility`) attached under the player, so new elements can be added later without rewriting the player.
- Constants that affect feel go in **`PlayerTuning` (a custom `Resource`)** with `@export` vars, never as magic numbers in code.
- Prefer **signals** for communication between objects (switch → door, player died → room manager). Avoid `get_node("../../..")` chains.

## Working rules
1. **Small steps.** One mechanic per task. Don't build ahead of the current stage in `PROMPTS.md`.
2. **Verify before saying done.** After editing, check for script errors (see "Running and checking" below). Never report success with errors in the output.
3. **Tell me how to test.** End each task with a short checklist: what to press and what I should see.
4. **Scenes (.tscn):** keep them simple. It's fine to write `.tscn` files directly, but prefer building small node trees in code (`_ready`) when that's clearer. Don't hand-edit resource UIDs; don't delete `.uid` / `.import` files — Godot manages them.
5. **Placeholder art only** (`ColorRect`, `Polygon2D`, `Line2D`, `CPUParticles2D`) using the color key in `GAME_DESIGN.md` §2.
6. **Git:** after each stage that works, suggest a commit message (don't commit unless I say so).
7. **Level editor palette (since Stage L3):** any stage that adds a placeable object or terrain layer adds its entry to `scenes/editor/palette_catalog.gd` (`Level_editor.md` §6) and keeps `tests/editor_smoke_test.tscn` passing. That file is the only place the element stages and the editor track meet.
8. If something in the design doc seems wrong or won't feel good, say so and propose an alternative before building it.

## Debug agents (`.claude/agents/`)
Cheaper subagents that run in their own context and return a short report. Use them instead of doing this work inline:
- **`test-runner`** (Haiku): after code changes, run the import check and smoke tests through it, not in the main conversation. Its report counts as the "verify before saying done" check; still never report success if it quotes ERROR lines.
- **`test-selector`** (Haiku, read-only): run it first after a change; it reads the git diff and returns only the tests (and Water sections) that change needs. Hand its list to `test-runner`. Run everything only before a commit/stage wrap-up or when I say "all".
- **`style-checker`** (Haiku, read-only): checks changed `.gd` files against the Code style rules above; lists file:line findings, clear vs judgement.
- **`perf-checker`** (Haiku): runs only the Water budget sections (W1, W2, W7b), compares with `tests/perf_history.txt` and appends to it. Use after water changes.
- **`godot-debugger`** (Sonnet, read-only): a failing smoke test, a SCRIPT ERROR you can't explain at a glance, or a bug I report from play-testing goes to it first. Apply and explain its proposed fix in the main conversation, then confirm with `test-runner`.
- **`room-inspector`** (Sonnet): room screenshots and visual checks (e.g. step 6 of `/room`).
- Skills: `/check` (tests, picks relevant ones by default), `/wrapup <stage>` (end of a stage: all tests, style, budget, palette, docs sync, commit message), `/playtest <notes>` (sorts my notes into bug / tuning / design, logs them in `PLAYTEST_LOG.md`), `/stage`, `/room`.
- Don't delegate trivial things: a single `--check-only` on one script, reading one error line, or a fix whose cause is already obvious is cheaper inline.
